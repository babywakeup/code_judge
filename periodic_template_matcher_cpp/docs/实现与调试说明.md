# 已做的准备、C++ 实现与调试入口

## 先理解代码如何连接

```text
Python 调用 PeriodicTemplateMatcher.match()
  → api.py：传递参数、复用原有结果类和文件输出
  → bindings/module.cpp：校验 NumPy 数组、复制数据、释放 GIL
  → src/pipeline.cpp：执行 C++ 七步流水线
      配准 → 实例定位 → 标签迁移 → 周期补全 → 实例支持补全 → 融合
  → bindings/module.cpp：把拥有独立内存的数组交回 Python
```

GT 只进入评价，不参与匹配。C++ 核心没有调用 Python 匹配算法；Python 外层继续复用配置、LabelMe/图像文件输入、结果类、保存和查看器。

## 哪些是写 C++ 必需的

| 内容 | 为什么要有 | 是否强制 |
| --- | --- | --- |
| 编译器与链接器 | 把 `.cpp` 变成机器代码并连接依赖 | C++ 必需 |
| OpenCV C++ 头文件、库 | 调用 GaussianBlur、ECC、warpPerspective 等 | 本项目必需 |
| 图像类型、步长、内存所有权约定 | Python 和 C++ 必须用同一种方式解释像素 | 跨语言调用必需 |
| 调试器、符号、对应的源码 | 支持断点、单步和变量查看 | debug 要求必需 |
| CMake / Ninja | 管理编译参数、目标及增量构建 | 工具选择，可替代 |
| pybind11 | 将 C++ 数组接口包装为 Python 模块 | 工具选择，可用 ctypes 等替代 |
| 对照测试 | 证明移植后的行为对应 | 本次复现验收必需 |
| clang-format | 将代码整理为可逐行调试的形式 | 可选开发工具 |

当前本机构建使用 Zig 提供的 Clang C++ 编译器，并用同一套工具构建 OpenCV。没有要求安装整套 Visual Studio。

## 编译后产生什么

- `ptm_core`：静态核心库，存放全部算法。Python 扩展和调试程序使用同一份核心。
- `_native.cp312-win_amd64.pyd`：Windows 的 CPython 扩展，可像 Python 模块一样导入；不是原案例中通过 ctypes 查函数的普通 DLL 接口。
- `ptm_debug.exe`：独立 C++ 调试程序，不需要先启动 Python。
- `.pdb` 等符号文件：调试器用它把机器指令关联回源码和变量。

Debug 和 Release 分别在 `build/debug`、`build/release` 编译。各自的扩展保存在对应目录的 `python/` 下；`build.py` 会把本次选择的扩展复制到包目录，并在 `build/active-native.json` 记录配置、来源和哈希。切换配置不再需要清理另一种构建。切换前结束已导入扩展的 Python 进程。

## 从哪里开始断点

先打开 `ptm.code-workspace`，使用 CodeLLDB 扩展启动 `PTM: built-in smoke`。

1. 在 `debug/main.cpp` 调用 `ptm::match` 的行设置断点。
2. 进入 `src/pipeline.cpp` 的 `match`，观察 `inputs` 和 `cfg`。
3. 进入 `src/registration.cpp` 的 `features`、`translation_peaks`、`refine`、`score`。
4. 进入 `src/objects.cpp` 观察身份候选与循环顺序选择。
5. 进入 `src/periodic.cpp` 查看每个副本的几何批准、标签批准和局部验证。

不安装 VS Code 扩展也可以用 `tools/verify_debugger.py` 验证实际断点命中；它会检查停止原因、源码行及继续后的退出状态。

## 本机命令（项目根目录 PowerShell）

```powershell
# 已准备好的开发环境：编译、运行与调试
.\.venv\Scripts\python.exe .\periodic_template_matcher_cpp\build.py --config Debug
.\periodic_template_matcher_cpp\build\debug\ptm_debug.exe
.\.venv\Scripts\python.exe .\periodic_template_matcher_cpp\tools\verify_debugger.py --backend cli

# 使用原来的配置与文件工作流
.\.venv\Scripts\python.exe -m periodic_template_matcher_cpp --config periodic_template_matcher/config.sd1.labelme.opencv.json --out periodic_template_matcher_cpp/build/result

# 测试
.\.venv\Scripts\python.exe -m unittest discover -s periodic_template_matcher_cpp/tests -v
.\.venv\Scripts\ctest.exe --test-dir periodic_template_matcher_cpp/build/debug --output-on-failure

# 性能测量应先编译 Release
.\.venv\Scripts\python.exe .\periodic_template_matcher_cpp\build.py --config Release
```

新电脑构建时先安装 `requirements-build.txt` 中的工具和匹配的运行依赖，再运行 `tools/prepare_native.py` 或提供自己的 `--opencv-dir`。仅部署时不用带编译器、头文件和 CMake；扩展仍然要求匹配的 Python 版本、操作系统和 CPU 架构。Linux 需要在兼容环境重新编译，不能复制 Windows 的 `.pyd`。

## 如何理解“功能对应”和浮点差异

相同输入、相同变换矩阵下，标签、掩码和 uint8 图像投影要求逐像素相同。已批准的匹配矩阵还要进行数值误差检查；标签、身份、未知区域、接受状态不能用“浮点误差”随意放宽。

但两边各自执行 ECC 优化后，矩阵未必逐位相同。即使 OpenCV 都是 4.14，不同编译器和优化内核也可能让中间舍入不同。已观察到相同首层 ECC 输入产生约 `2.086e-7` 的矩阵差异，后续迭代可能放大，尤其在基础匹配已经被拒绝的低置信度候选上。

因此，被拒绝的基础几何不作为定位精度承诺；仍检查它的投影图和有效掩码与它自己返回的矩阵严格对应。补充模板图像也按各自批准的矩阵验证精确拼接；独立优化后的两张展示图另在差异报告中记录，不假称逐像素相等。匹配阈值没有为通过测试而下调。

真实 SD-1 数据的精确差异由 `tools/compare_parity.py` 输出：**退出 0 只表示测量完成，不表示所有数组完全一致**。最终已验证项目、结果差异和未验证平台见 `status.md`。
